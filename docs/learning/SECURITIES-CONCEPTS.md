# 프랍 트레이딩으로 배우는 증권업 — 개념과 코드 매핑

기준일: 2026-11-14 · 대상: 이 프로젝트를 만들며 증권업의 업무 구조를 이해하려는 개발자

프랍 평가 서비스는 작지만 증권업의 핵심 업무를 거의 다 축소해서 담고 있다. **주문을 받고, 위험을 사전에 막고, 체결하고, 포지션을 회계 처리하고, 시가로 평가하고, 한도를 넘으면 강제로 정리하고, 하루를 마감하고, 돈을 정산한다.** 이 문서는 각 업무를 실제 증권업의 개념과 연결하고, 그 개념이 이 프로젝트의 어느 코드에 들어 있는지를 짚는다.

> 법령·제도 설명은 개념 이해용 요약이다. 조문 번호와 세부 수치는 원문으로 확인한 뒤 인용한다. 확인 전 항목은 `[확인 필요]`로 표시했다.

## 0. 업의 지도: 누가 누구의 돈으로 무엇을 하는가

| 업무 | 누구의 돈·위험인가 | 실제 증권업의 예 | 이 프로젝트에서 |
| --- | --- | --- | --- |
| 위탁매매(브로커리지) | 고객 돈, 고객 위험. 회사는 수수료 수익 | 증권사가 고객 주문을 거래소에 전달 | 하지 않는다(실주문 없음) |
| 자기매매(딜링, 고유계정) | 회사 돈, 회사 위험 | 증권사 트레이딩 부서, 기관 프랍 데스크 | 하지 않는다 |
| 투자자문·일임 | 고객 돈, 고객 위험, 회사는 판단 제공·대행 | 자산운용, 랩어카운트 | 하지 않는다(조언 금지 원칙) |
| **리테일 프랍 평가** | 고객은 평가 수수료만 위험. 거래는 시뮬레이션 | 해외 평가형 프랍 업체 | **이 서비스** |

리테일 프랍은 "트레이더를 고용하는 자기매매 데스크"를 흉내 내지만, 실제로는 **시뮬레이션 환경에서 위험관리 규율을 평가하는 서비스**다. 그래서 회사의 핵심 역량이 "시장 예측"이 아니라 **규칙 판정·체결 시뮬레이션·지급 재무관리**가 된다. 증권사로 치면 프런트(트레이딩)가 아니라 **미들(리스크)·백(결제·회계) 오피스**의 업무다.

| 증권사 조직 | 하는 일 | 이 프로젝트의 대응 |
| --- | --- | --- |
| 프런트 오피스 | 주문 접수, 트레이딩 | 주문 화면, `placeOrder` |
| 미들 오피스 | 한도 관리, 위험 측정, 손익 확인 | 규칙 엔진 `src/rules/engine.js`, 주문 전 위험 검사 |
| 백 오피스 | 체결 확인, 결제, 회계, 정산, 기록 보관 | 이벤트 로그, 원장(04-money 설계), 거래일 마감 |
| 준법감시(컴플라이언스) | 법규·내부통제 점검, 부정거래 감시 | 출시 게이트, 부정거래 신호(data) |

## 1. 시세와 호가

| 개념 | 설명 | 코드 |
| --- | --- | --- |
| 매수호가(bid)·매도호가(ask) | 지금 당장 팔 수 있는 가격과 살 수 있는 가격 | `onQuote({ bid, ask })` |
| 스프레드 | ask − bid. 즉시 거래하는 비용의 일부 | 시장가 매수는 ask, 매도는 bid에서 체결 |
| 호가 단위(틱) | 가격이 움직일 수 있는 최소 단위 | `priceDecimals`, 정수 틱으로 저장 |
| 시세 지연·이상치 | 피드 단절, 역전 호가(bid > ask) | `status: 'delayed'` 시 주문·트리거 중단, 역전 호가 `quote_rejected` |
| 시세 라이선스 | 거래소 시세는 재배포에 계약이 필요 | data 계획 3.1 소스 선정 기준 |

배울 점: 증권 시스템에서 "가격"은 하나가 아니다. 사는 가격, 파는 가격, 마지막 체결가, 정산가가 다르고, **어떤 가격으로 무엇을 계산하는지**를 매번 정해야 한다. 이 프로젝트는 평가에 "지금 청산하면 받을 가격"(롱은 bid, 숏은 ask)을 쓴다.

## 2. 주문과 체결

| 개념 | 설명 | 코드 |
| --- | --- | --- |
| 시장가 주문 | 가격 지정 없이 즉시 체결. 체결가 불확실 | `type: 'market'`, 슬리피지 적용 |
| 지정가 주문 | 이 가격 또는 더 좋은 가격에서만 체결 | `type: 'limit'`. 즉시 체결 가능하면 더 좋은 호가로(`limit_marketable`) |
| 스톱 주문(역지정가) | 가격이 트리거에 닿으면 시장가로 전환 | `type: 'stop'` |
| 슬리피지 | 기대 가격과 실제 체결가의 차이 | `slippageBps`, 항상 트레이더에게 불리한 방향 |
| 갭 | 가격이 연속되지 않고 건너뜀 | 손절가를 지나친 첫 시세로 체결 — 손절이 손실 상한을 보장하지 않음을 테스트로 고정 |
| OCO(One-Cancels-Other) | 손절·익절 중 하나가 체결되면 다른 하나 취소 | `ocoGroup`, `order_cancelled reason: 'oco'` |
| 청산 전용(reduce-only) | 포지션을 늘리거나 뒤집을 수 없는 주문 | `reduceOnly` 검사 |
| 멱등성 | 같은 주문이 두 번 접수되는 사고 방지 | 주문 id 중복 시 `idempotency_conflict` |

## 3. 주문 전 위험관리 (Pre-trade risk control)

증권사는 주문을 시장에 내보내기 **전에** 자동으로 한도를 검사한다. 미국에서는 SEC의 Market Access Rule(Rule 15c3-5)이 시장 접근을 제공하는 브로커에게 이런 사전 통제를 요구한다. 국내 증권사도 주문 수량·금액 한도, 증거금 확인 등 사전 점검을 운영한다 `[확인 필요: 국내 근거 규정]`.

| 검사 | 막는 사고 | 코드 |
| --- | --- | --- |
| 계정 상태 | 종료·정지된 계정의 주문 | `account_closed` |
| 시장 상태 | 시세가 비정상일 때의 주문 | `market_delayed` |
| 수량 정밀도 | 단위 오류(팻 핑거) | `invalid_precision` |
| 최대 보유 수량·명목 금액 | 과도한 집중 | `max_position` → `order_rejected_rule` |
| 레버리지(증거금) | 자본 대비 과도한 노출 | `notional > equity × maxLeverage` → `insufficient_margin` |
| 방향 검증 | 손절가가 잘못된 쪽에 있는 주문 | `#checkProtection` |

배울 점: **줄이는 주문은 항상 허용한다**(`abs(projected) <= abs(current)`이면 통과). 위험을 줄이려는 행위를 위험 통제가 막으면 안 된다는 것이 위험관리의 기본 원칙이다.

## 4. 포지션 회계

| 개념 | 설명 | 코드 |
| --- | --- | --- |
| 롯(lot) | 한 번의 체결로 생긴 보유 단위 | `#applyLots` |
| FIFO | 먼저 산 것부터 판 것으로 본다 | 반대 방향 체결은 가장 오래된 롯부터 상계 |
| 평균단가 | 남은 롯의 가중평균 가격 | `snapshot().positions[].averagePrice` |
| 실현손익 | 청산으로 확정된 손익 | `realizedPnlCents`, 잔고에 반영 |
| 평가손익(미실현) | 현재 시세로 계산한 보유분 손익 | `unrealizedPnlCents` |
| 잔고(balance) vs 에쿼티(equity) | 잔고 = 확정 금액, 에쿼티 = 잔고 + 평가손익 | 규칙 엔진은 둘을 구분해 판정 |
| 넷팅(one-way) | 종목당 하나의 순포지션 | 같은 종목 매수·매도는 상계 |

배울 점: 원가 산정 방식(FIFO, 이동평균, 개별법)에 따라 **같은 거래도 실현손익이 달라진다.** 국내 개인 주식 계좌는 보통 이동평균 단가로 보여 주고, 미국 선물·외환은 FIFO를 쓰는 경우가 많다 `[확인 필요]`. 회계 방식은 반드시 명시해야 하는 계약 조건이다. `positions close FIFO by lot` 테스트가 그 계약이다.

## 5. 시가평가와 반올림

| 개념 | 설명 | 코드 |
| --- | --- | --- |
| 시가평가(Mark-to-market) | 보유 자산을 현재 시세로 다시 평가 | 시세마다 `mark_to_market` 이벤트 |
| 일일정산 | 선물은 매일 정산가로 손익을 주고받는다(변동증거금) | `closeTradingDay` → `trading_day_closed` |
| 반올림 정책 | 금액 계산의 단수 처리 | `src/rules/money.js`: 손실선 올림, 실현이익 내림, 수수료 올림 |
| 정수 금액 | 부동소수점 오차가 경계 판정을 바꾸지 않도록 | 모든 금액 BigInt 센트 |

배울 점: 금융 코드의 반올림은 기술 문제가 아니라 **누구에게 유리하게 할 것인가의 정책**이다. 이 프로젝트는 "트레이더에게 실제보다 여유가 있다고 말하지 않는다"를 원칙으로 방향을 정했고, 함수마다 주석으로 적었다.

## 6. 위험 한도와 강제 청산

| 프랍 규칙 | 증권업의 원형 | 코드 |
| --- | --- | --- |
| 일일 손실 한도 | 딜링룸의 트레이더별 일일 손실한도(로스컷) | `daily_loss` |
| 최대 손실(고정) | 트레이더에게 배정한 위험 자본의 총 한도 | `max_loss_static` |
| 추적형 최대 손실 | 고점 대비 낙폭(drawdown) 관리 | `max_loss_trailing` (장중·종가, 초기 잔고 고정) |
| 강제 청산 | 증거금 부족 시 반대매매, 로스컷 도달 시 포지션 정리 | `#liquidateAll` — 강제 청산도 슬리피지를 낸다 |
| 소프트 일일 한도(당일 정지) | 손실한도에 닿은 트레이더의 당일 신규 거래 중지 | `daily_loss.enforcement: 'pause'` — 청산 후 다음 거래일까지 주문 거부 |
| 장 마감 전 청산 | 오버나이트 위험 한도, 선물의 세션 단위 운용 | `flat_at_close` |
| 등호 처리 | 한도와 정확히 같으면? | 도달로 본다(`<=`) — 공용 예시로 고정 |

배울 점: 한도는 "넘으면 막는다"가 아니라 **"넘은 순간의 시세로 정리하고, 그 결과는 한도보다 나쁠 수 있다"**까지가 한 세트다. 강제 청산 테스트에서 최종 잔고가 한도선보다 더 내려가는 이유가 그것이다(갭 + 슬리피지).

## 7. 거래일·결제·정산

| 개념 | 설명 | 이 프로젝트 |
| --- | --- | --- |

| 대사(reconciliation) | 내부 기록과 외부(PG·은행) 기록 일치 확인 | 일일 대사 작업 설계 |

## 8. 기록·감사·재현

증권사는 주문·체결 기록을 일정 기간 보관하고, 분쟁 시 당시 상황을 재현할 수 있어야 한다 `[확인 필요: 국내 보존 기간 규정]`.

- 이 프로젝트의 대응: 모든 상태 변화를 순번이 있는 이벤트로 남기고(`events`, `seq`), 규칙 엔진은 시계·난수를 읽지 않는 순수 함수다. 같은 이벤트를 재생하면 같은 판정이 나온다(`replay`).
- 판정 근거(`thresholdCents`, `observedCents`, `ruleId`)를 판정 이벤트에 함께 남긴다.
