# Oh My Prop — 제품 기획 및 실행 계획

## 현재 확인된 사실

- Oh My Prop은 프랍 트레이딩을 위한 Oh My 시리즈 제품이다.
- 공개 GitHub 조직에는 `frontend` 저장소 하나가 있으며, 확인 시점의 저장소는 비어 있다. 현재 작업 디렉터리에도 기존 소스가 없다.
- 대상 사용자, 프랍 트레이딩의 운영 모델, 거래 시장과 관할권, 데이터·주문 연결 방식은 아직 결정되지 않았다.

## 제품 결정을 위한 핵심 질문

**우선 고객과 운영 모델을 결정한다.** 다음은 서로 다른 제품이며 계좌·규정·보안·데이터 요구사항이 크게 다르다.

1. **트레이더용 동반 도구:** 여러 프랍 업체의 평가·펀디드 계좌에서 손실 한도, 거래 일지, 성과를 관리한다. 프랍 업체나 중개사를 사칭하지 않는다.
2. **프랍 업체 운영 플랫폼:** 업체가 평가 프로그램, 계좌, 규정, 위반, 정산을 운영한다. 관리자와 트레이더 간 권한 분리 및 감사가 필수다.
3. **자체 자본 운용 데스크:** 팀의 실제 자본, 포지션, 주문, 위험 한도를 운영한다. 실거래 통제와 운영 책임이 초기 설계의 중심이다.

아래 제안은 의사결정을 돕기 위한 **트레이더용 동반 도구 가설**이지 확정 범위가 아니다. 실제 사용자와 거래 환경을 확인한 뒤 수정한다.

## 제품 가설: 계좌 위험 가시화

- **문제:** 트레이더는 업체별로 다른 일일 손실, 최대 손실, 리셋 시각과 평가 목표를 동시에 관리하며, 손익 숫자만으로 위반 여부를 판단하기 어렵다.
- **핵심 가치:** 사용자가 입력하거나 검증된 연결에서 가져온 계좌 상태와 명시적인 규칙을 함께 보여 주고, 데이터의 시점과 출처를 숨기지 않는다.
- **초기 대상:** 한 개 이상의 평가 계좌를 수동으로 추적하는 개인 트레이더. 자산군과 지역은 사용자 조사로 확정한다.
- **성공 가설:** 사용자가 자신의 규칙을 설정하고 현재 수치와 잔여 위험을 이해해 반복적으로 확인한다. 활성화·재방문 및 계산 불일치 제보를 측정하되 목표치는 실제 기준선 확인 후 정한다.
- **검증 방법:** 서로 다른 업체의 실제 규칙을 가진 트레이더 인터뷰와 비식별 계좌 예시로 규칙 해석 및 계산 결과를 검토한다. 공식 약관과 버전을 확인하기 전에는 업체별 템플릿을 확정하지 않는다.

## 첫 번째 검증 가능한 범위

확정된 고객 모델이 위 가설과 일치할 경우, 실제 규칙 사례를 확보한 후 다음 순서로 구현한다.

1. 계좌의 통화, 기준 잔고와 수동 스냅샷(잔고, 평가손익 포함 여부, 시각)을 기록한다.
2. 지원할 손실 규칙을 계산식, 기준값, 리셋 시간대 및 포함 손익에 이르기까지 명시적으로 설정한다. 불명확하거나 지원하지 않는 규칙은 정상·안전으로 판정하지 않는다.
3. 현재 스냅샷 기준의 한도와 잔여 금액, 사용한 입력값·기준 시각을 표시한다. 데이터 누락·오래됨과 계산 불가를 명확히 구분한다.
4. 저장·수정·삭제 및 새로고침 후 복원 경로를 실제 사용 흐름으로 검증한다. 브라우저 로컬 저장을 택한다면 기기별 데이터이고 분실될 수 있음을 표시한다.

초기 범위에서 실거래 주문, 자금 보관, 자동매매, 업체별 규정 준수 보증, 수익 보장, 자동 계좌 연동은 제외한다. 거래 차단이나 실시간 알림은 신뢰할 수 있는 실시간 데이터와 운영 체계가 확보되기 전까지 약속하지 않는다.

## 규칙 모델에서 먼저 확인할 사항

- 일일 손실의 기준: 당일 시작 잔고·에쿼티·초기 잔고 중 무엇인지, 실현·미실현 손익과 수수료·스왑 포함 여부.
- 최대 손실의 기준: 고정 또는 추적형, 고점 계산 시점, 추적 중단 조건, 잔고와 에쿼티의 관계.
- 리셋의 거래일 경계, IANA 시간대, 서머타임 및 주말 처리.
- 위반 판정의 등호 포함 여부, 통화·정밀도·반올림, 데이터 지연 및 거래 중 변동.
- 규칙의 출처 URL, 적용 상품·계좌 유형, 효력일 및 마지막 검증일. 업체가 규칙을 바꿨을 때 과거 기록과 새 버전을 혼동하지 않는다.

일일 시작점 또는 추적 고점 등 필수 입력이 없으면 남은 한도를 추측하지 않는다. 음수 잔여 금액은 위반 가능성을 나타내지만, 수동 데이터만으로 업체의 공식 판정이라고 표시하지 않는다.

## 기술 및 운영 원칙

- 프론트엔드 저장소의 기술 스택은 비어 있으므로 확정되지 않았다. 고객 모델과 첫 흐름을 정한 뒤 설치·배포 환경을 포함해 선택한다.
- 금액은 부동소수점 오차를 피하는 표현과 명시적 반올림을 사용한다. 계산 로직과 화면을 분리하고 경계값, 시간대, 규칙 버전 변경 사례를 검증한다.
- 손익과 계좌 식별자는 민감한 금융 정보로 취급한다. 필요한 데이터만 수집하고 저장 위치·보존·삭제 정책을 공개한다. 브로커 비밀번호를 임의로 수집하지 않는다.
- 외부 연동 전 공급자의 공식 API, 권한, 약관, 지연·장애 시 동작을 확인한다. 비밀키는 클라이언트에 배포하지 않는다.
- 제품 설명은 정보 제공과 업체의 공식 판정을 구분한다. 관할권과 사업 모델 확정 후 법률·규제·개인정보 검토를 받는다.

## 이번 실행의 결정

사용자의 학습·도메인 탐색 목적과 장기 실운용 가능성을 고려해, 첫 구현은 실제 계좌나 주문에 연결하지 않는 고정 손실 한도 학습용 시뮬레이터로 정한다. 프랍 업체 운영 시스템이나 실거래 인프라를 추정해 구축하지 않는다. 가상의 규칙과 수동 스냅샷을 사용하며 실제 업체의 승인·위반 판정이 아니다. 자동 리셋·추적형 손실·실시간 시세는 구현하지 않는다. 실제 운용 전에는 특정 업체의 공식 규정·실시간 데이터·장애 대응·법률 검토가 별도로 필요하다.

### 선택 근거와 참고 자료

- 공개 저장소 [sk-portwise](https://github.com/minkyu-k530/sk-portwise)는 바닐라 JavaScript와 렌더링에서 분리된 시뮬레이션을 사용하고, [demurrage-desk](https://github.com/minkyu-k530/demurrage-desk)는 가상 데이터의 한계를 명시한다. [SKALA-Vue.js](https://github.com/minkyu-k530/SKALA-Vue.js)는 Vue 경험을 보여 준다. 단순 계산 화면에는 빌드가 필요 없는 JavaScript 모듈이 학습과 실행에 충분하므로 이를 선택했다. 공개 저장소만으로 개인의 실거래 경험을 판단하지 않는다.
- 업체별 규칙은 서로 다르다. [FTMO 공식 설명](https://ftmo.com/en/trading-objectives/)의 2-Step은 일일 기준이 리셋 시 잔고이고 초기 자본 기준 고정 최대 손실을 사용하지만, 1-Step은 최대 손실 기준이 추적된다. [Topstep의 최대 손실 설명](https://help.topstep.com/en/articles/8284204-what-is-the-maximum-loss-limit)은 별도의 추적·정지 조건을 설명한다. [The5ers High Stakes FAQ](https://the5ers.com/faqs/what-is-the-maximum-loss-and-the-maximum-daily-loss-in-the-high-stakes-program/)의 일일 기준도 다르다.
- 따라서 구현한 일일 시작 **에쿼티** 기반 식은 위 업체들의 공식 규칙 템플릿이 아니다. 등호 포함도 학습용 보수적 가정이며 업체별 실제 판정과 다를 수 있다. 스냅샷 사이의 위반은 관찰할 수 없다.
- 첫 화면은 입력을 저장하지 않는 실험 도구로 정했다. 위의 저장·복원 흐름은 제품 가설의 후속 후보이며 이번 구현의 기능이 아니다.

### 실행 결과

- `frontend`에 손실 한도 시뮬레이터와 정수 센트 계산 엔진을 구현했다. 기본 가상 값은 초기 잔고 $100,000, 일일 시작 에쿼티 $100,000, 현재 에쿼티 $98,500, 손실률 5%와 10%다.
- `npm test`: 계산, 경계, 입력 검증과 반올림을 포함한 7개 테스트 통과.
- 로컬 브라우저에서 기본 한도 $95,000/$90,000과 잔여 $3,500, 한도에 정확히 도달한 경우, 한도 아래 $1,000인 경우, 잘못된 입력 시 결과 숨김을 확인했다. 390px 화면에서 문서 너비가 화면 너비를 넘지 않는 것과 브라우저 오류가 없는 것도 확인했다.
- 화면은 한 시점의 입력만 계산하며, 저장·스냅샷 이력·실시간 감시·실거래는 제공하지 않는다. 다음 단계는 실제 대상 시장과 업체의 규칙을 하나씩 명세하고 리셋·추적·계좌 자료의 출처를 검증하는 일이다.

## 다음 학습 단계: 일일 리셋과 미실현 손익

- **문제:** 잔고와 에쿼티를 혼동하거나 리셋 전의 한도를 다음 거래일에도 그대로 적용하면, 포지션이나 시세가 그대로여도 달라지는 위험을 놓친다.
- **근거:** [FTMO CFD 2-Step 공식 설명](https://ftmo.com/en/trading-objectives/)은 일일 한도선을 00:00 CE(S)T 잔고에서 초기 가상 자본의 5%를 뺀 값으로 재산정하고, 최대 손실 한도는 초기 가상 자본의 90%로 고정한다고 설명한다. 에쿼티에는 열린 포지션 손익과 스왑·수수료가 반영된다. 공식 설명의 위반 표현은 한도선 *미만*이다.
- **결정:** 기존의 임의 규칙 계산기와 별도로, 전일 기준 잔고와 새 기준 잔고를 직접 입력하고 같은 에쿼티를 전후에 적용하는 교육용 비교를 만든다. 시각 자동 계산, 거래 이력, 스왑·수수료 개별 계산이나 공식 판정은 구현하지 않는다. 초기값은 자본 $100,000, 전일 잔고 $100,000, 새 잔고 $102,000, 에쿼티 $96,000이다. 따라서 일일 한도선은 $95,000에서 $97,000으로 바뀌고, 에쿼티가 그대로여도 한도선 아래가 될 수 있다.
- **범위:** 이 비교는 개별 스냅샷만 다룬다. 그 사이의 위반 여부, 실제 리셋 시각의 계좌 값 및 다른 평가 조건을 알 수 없으며, 공식 규칙은 바뀔 수 있다. 소수 센트가 발생한 한도는 기존 계산기와 같이 보수적으로 올림한 학습 모델이다.

### 구현 및 검증 결과

- 리셋 전후의 잔고와 비교 에쿼티를 편집하는 화면과 계산을 추가했다. 일일·최대 한도 각각에 대해 한도선, 차액과 위·같음·아래 상태를 표시한다.
- `npm test`에서 기존 계산기와 리셋 시나리오를 포함한 11개 테스트가 통과했다. 브라우저에서 기본 예시의 $95,000 → $97,000, 차액 +$1,000 → −$1,000, 한도선과 같을 때의 별도 표시 및 잘못된 입력 시 결과 숨김을 확인했다. 390px 화면의 가로 넘침과 브라우저 오류가 없음을 확인했다.

## 가상 거래 연습장

- **문제:** 단일 시점의 잔여 한도만 보면 손익이 회복됐을 때 과거에 한도에 도달한 사실을 놓칠 수 있다. 위험 관리에는 순서가 있는 거래 기록이 필요하다.
- **결정:** 한 번의 가상 세션에서 초기 잔고와 고정 손실률을 설정하고, 이미 청산한 가상 거래의 순손익을 순서대로 입력한다. 각 기록 후 잔고와 한도까지의 차액을 재계산하고, 한도에 도달한 최초 기록은 이후 수익이 나도 표시한다.
- **가정:** 가상 한도선 = 초기 잔고 − 초기 잔고 × 손실률. 한도 도달도 경계로 본다. 거래별 순손익은 사용자가 수수료 등을 이미 반영한 값이다. 미실현 손익, 가격, 거래 실행, 실제 업체별 규정과 거래일 리셋은 다루지 않는다.
- **데이터:** 입력은 브라우저 로컬 저장소에만 보관한다. 동기화·백업이 아니며 개인 금융정보를 입력하는 용도가 아니다. 기록을 삭제하면 남은 기록을 처음부터 재계산하므로 과거 한도 도달 표시도 달라질 수 있다.

### 구현 및 검증 결과

- 별도 연습장에 설정, 거래 추가·개별 삭제·전체 삭제, 순서별 잔고 재계산, 최초 한도 도달 기록 및 로컬 저장을 구현했다. 저장소를 읽거나 쓸 수 없을 때는 화면에 경고한다.
- `npm test`의 19개 테스트가 통과했다. 브라우저에서 $100,000 세션에 −$5,000 후 +$6,000을 입력해 한도 도달 이력이 회복 후와 새로고침 후에도 유지됨을 확인했다. 첫 거래를 삭제하면 남은 기록을 재계산해 이력이 사라지는 것도 확인했다. 390px 화면에 가로 넘침과 브라우저 오류가 없었다.

## 연습 기록 백업과 복원

- **문제:** 로컬 저장소는 브라우저 데이터 삭제나 기기 변경을 견디는 백업이 아니다. 가상 거래 기록을 유지하거나 다른 기기에서 검토하려면 사용자가 직접 옮길 수 있어야 한다.
- **결정:** 가상 세션 설정과 순서 있는 거래 기록만 버전이 명시된 JSON 파일로 내보내고, 가져온 파일은 종류·버전·크기·계산 가능성을 검증한다. 복원은 현재 세션 전체를 대체하므로 사용자 확인을 받은 뒤에만 진행한다.
- **안전 조건:** 취소, 잘못된 파일 또는 저장 실패 시 기존 기록을 바꾸지 않는다. 읽을 수 없는 로컬 데이터는 덮어쓰지 않는다. 파일은 암호화되지 않으므로 민감한 내용을 넣지 않고 안전하게 보관해야 한다. 서버나 클라우드 연동은 없다.

### 구현 및 검증 결과

- JSON 백업 내보내기와 확인 후 전체 세션 복원을 추가했다. 형식 버전, 1 MiB 제한 및 거래 계산을 검증하고, 로컬 저장에 성공한 뒤에만 화면의 세션을 교체한다.
- `npm test` 25개가 통과했다. 브라우저에서 실제 내보내기 경로가 생성한 JSON 내용, 가져오기 후 새로고침, 잘못된 파일, 복원 취소와 저장 실패 시 기존 잔고가 유지되는 것을 확인했다. 390px 화면에서 가로 넘침과 브라우저 오류가 없었다.
