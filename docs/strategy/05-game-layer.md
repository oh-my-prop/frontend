# 05. 게임 레이어 — 트랙 레이스 모델

기준일: 2026-11-23 · 상태: **보류**(착수 일정 없음) · 상위 문서: [전환 전략](README.md)

> **보류 — 2026-11-23**
>
> 우선순위를 **런칭(유료 평가·수익 경로)**으로 되돌렸다. 이 문서는 설계 기록으로 남기되 **착수 일정을 가지지 않는다.** 7절의 R0~R5는 로드맵([04](04-roadmap-and-metrics.md) §1)과 평행하게 진행되지 않는다.
>
> **이미 들어간 것**(`main`에 병합됨, 되돌리지 않는다)
>
> - `data` — 트랙 추출 도구 `scripts/track.js`, `npm run track:extract`, `npm run track:synth`, 첫 트랙 `tracks/BTC-PERP/btc-perp-20261123-1200-300s`
> - `backend` — `npm run dev:sim -- --track`(개발 스크립트 전용. 서버 코드는 바뀌지 않았다)
>
> 둘 다 **고정된 호가 구간을 그대로 재생하는 도구**다. 같은 입력에 같은 결과가 나오므로 체결·한도 판정의 회귀 테스트와 디버깅에 게임 레이어와 무관하게 쓸모가 있다. 그래서 남긴다.
>
> **재개 조건**: 유료 평가(G1)가 돌아가고, 그러고도 남는 유입·리텐션 문제가 실측으로 확인될 때. 그 전까지 R0~R5에는 일정을 붙이지 않는다.

아래는 보류 시점까지 정리한 설계다. 이 문서는 "카트라이더 같은 게임성"을 Oh My Prop에 얹는 방법을 정의한다. 대상은 **G0(무료) 범위**이며, 유료 평가·보상 지급(G1·G2)과는 기능 플래그로 분리한다. 기존 전략 문서(01~04)의 결정은 유지하고, 이 문서는 그 위에 레이어 하나를 추가한다.

## 한 줄 결론

> **14일 시즌 하나를 10분짜리 트랙 레이스 수백 판으로 쪼갠다.** 트랙은 보관된 과거 시세 구간이고, 레이스는 모두가 같은 구간을 같은 속도로 받는 결정론적 매치다. 순위는 수익률 단독이 아니라 **완주(규칙 미위반) 우선**이다. 우연 요소·확률형 아이템·성능 과금·현금성 보상은 이 레이어에 넣지 않는다.

## 1. 무엇을 모방하고 무엇을 버리는가

카트라이더가 실제로 주는 것은 세 가지다.

| 카트라이더가 주는 것 | 현재 Oh My Prop | 갭 |
| --- | --- | --- |
| 2~3분 세션 → 즉시 재시작 → "한 판 더" | 14일 시즌. 첫 결과까지 수 시간~수 일, 재시작 개념 없음 | **크다** |
| 모두가 같은 트랙을 달려서 결과 차이가 실력으로만 설명됨 | 각자 다른 시각에 실시간 시세로 거래. 순위표가 시장 국면(운)을 보상 | **크다** |
| 라이선스·티어로 숙련도를 외부에 증명 | `season → eval_1 → eval_2 → funded` 단계가 이미 라이선스 구조(`backend/src/trading/programs.js:14-36`) | 작다(화면만 없음) |

따라서 이 기획의 실제 작업은 **짧은 세션**과 **동일 조건 경쟁** 두 가지다. 라이선스는 기존 phase를 화면으로 드러내는 일에 가깝다.

버리는 것은 2절 매핑 표의 "비채택"과 6절이다.

## 3. 레이스 모델

### 3.1 트랙

- **원천**: 수집기가 이미 `data/raw/quotes/<YYYY-MM-DD>/<source>.jsonl`에 정규화 호가를 한 줄씩 보관한다(`data/collector/sinks.js:107-122`). 트랙은 이 파일에서 구간을 잘라 고정한 것이다. 새로 모을 데이터가 없다.
- **정의 필드**: `trackId`, `symbol`, `startTs`, `durationSec`, `speed`(1x·2x·4x), `quotesSha256`, `programVersion`, `publishedAt`.
- **불변성**: 규칙 명세와 같은 방식으로 내용 해시를 고정한다(`backend/src/trading/programs.js:59-74`와 동일 패턴). 트랙을 고치면 수정이 아니라 새 트랙이다. 같은 기록끼리만 비교할 수 있어야 고스트와 순위가 성립한다.
- **난이도 등급은 사후에 매긴다**: 실제 플레이의 위반율과 중앙 수익률로 등급을 정한다. 변동성 수치로 선험적 등급을 붙이면 "변동성이 큰 트랙일수록 많이 번다"는 암시가 되므로 하지 않는다.
- **표시 의무**: 트랙 화면과 매치 화면 상단에 "2025-07-14 BTC-PERP 구간 재생 — 과거 데이터이며 실시간 시세가 아닙니다"를 고정 표시한다. 기존 시뮬레이션 고지 바(전략 03 §4.1)와 같은 자리에 둔다.

### 3.2 매치

- 참가자 1~8명. 전원이 같은 트랙 · 같은 시작 시각 · 같은 초기 잔고 · 같은 규칙 버전을 받는다.
- 참가자마다 거래 계정 1개를 발급한다. phase는 기존 `season`을 재사용하지 않고 `race`를 신설한다. 시즌 순위 모집단(`backend/src/trading/service.js:100-101`)에 레이스 계정이 섞이면 두 순위가 같은 테이블을 공유하게 된다.
- **시세 주입이 유일한 비호환 변경**이다. 현재 `sim_inputs`의 `quote` 입력은 전역 시퀀스이고 모든 활성 계정에 적용된다(`backend/src/db.js:65-88`, `backend/src/trading/service.js:345-351`). 매치는 매치별로 격리된 호가 스트림이 필요하므로 `sim_inputs`에 `match_id`를 추가하고, `match_id`가 있는 호가는 해당 매치 참가 계정에만 적용한다. 기존 실시간 경로는 `match_id IS NULL`로 그대로 둔다.
- **결정론**: 규칙 엔진과 체결 엔진에 난수가 없다(`backend/src/execution/account.js:1-6`, `backend/src/rules/engine.js:1-12`). 같은 트랙 + 같은 주문 입력이면 센트까지 같은 결과가 나온다. 기동 시 재생 비교 로직(`backend/src/trading/service.js:190-235`)을 매치 결과 검증에 그대로 재사용한다.
- **연결 끊김**: 매치는 서버 시간으로 계속 진행한다. 재접속은 기존 SSE `Last-Event-ID` 복구(`backend/src/api-v2.js:35-64`)로 따라잡는다. 추가 구현이 필요 없다.
- **종료**: 트랙 마지막 호가에서 전 포지션을 강제 청산한다. `flat_at_close` 규칙이 이미 그 동작을 한다(`backend/src/execution/account.js:385-391`). 청산 후 결과를 확정한다.

### 3.3 점수 — 가장 중요한 설계 결정

수익률만으로 순위를 매기면 **한 번에 최대 사이즈로 거는 참가자가 1등**이 된다. 북극성 지표("규칙을 이해하고 지킨 계정 수", 04 §3)와 정면으로 충돌한다. 따라서 순위는 2단 정렬이다.

1. **완주자가 위반자보다 항상 위.** 완주 = 매치 종료까지 어떤 규칙도 위반하지 않음.
2. 완주자끼리: `returnBps` 내림차순(기존 산식 `backend/src/trading/service.js:584-595` 재사용).
3. 동률: 최대 잔고 하락률이 작은 순 → 한도 잔여 비율이 큰 순.
4. 위반자끼리: 위반 시각이 늦은 순.

효율 지표(`returnBps` 대비 최대 잔고 하락률)는 **순위에 넣지 않고 배지 조건으로만** 쓴다. 순위표를 두 개 만들면 "어느 쪽이 진짜 1등인가"가 생긴다.

레이팅(R4)은 수익률이 아니라 **완주율과 상대 순위**의 함수로 계산한다. 수익률을 레이팅에 직접 넣으면 티어가 운을 누적한다.

### 3.4 고스트

- 같은 트랙의 다른 기록을 시간축에 겹쳐 에쿼티 곡선으로 재생한다. `account_events`를 순서대로 재생하면 되므로 **새로 저장할 데이터가 없다**.
- 대상: 내 최고 기록 / 그 트랙 1위 기록 / 완주자 중앙값 곡선.
- **노출 제한**: 상대의 진입가·수량·주문 시점은 매치가 끝난 뒤에만, 그것도 곡선 형태로만 보여 준다. 실시간으로 상대 포지션을 보여 주면 그게 복사거래이고, 부정거래 탐지가 잡아야 할 행태(`data/analysis/features.js:13-29`의 `copyShare`)를 우리가 제품 기능으로 만드는 셈이 된다.

## 4. 라이선스

기존 phase에 이름과 화면을 붙인다. 내부 모델은 바꾸지 않는다.

| 라이선스 | 내부 phase | 승급 조건(결정 대기) |
| --- | --- | --- |
| 루키 | `season` | 가입 즉시 |
| L3 | `eval_1` | 서로 다른 트랙 5개 완주 + 누적 순이익 ≥ 0 |
| L2 | `eval_2` | L3 규칙으로 수익 목표 달성 |
| L1 | `funded` | L2 규칙으로 수익 목표 달성. G2 전까지 보상 없이 표식만 |

두 가지를 못 박는다.

- **라이선스 시험은 레이스가 아니다.** 카트라이더의 라이선스 시험도 경주가 아니라 단독 과제다. 여기서는 기존 평가 규칙(일일 손실·최대 손실·최소 거래일·수익 목표)을 그대로 쓴다. 레이스는 연습이고 라이선스는 증명이다.
- **돈으로 라이선스를 사게 하지 않는다.** 유료 평가 구매가 라이선스 승급의 유일한 경로가 되면 지불 능력이 등급이 된다. 무료 트랙 완주만으로 L2까지 도달할 수 있어야 한다.

## 5. 로비

- 채널 = 라이선스 등급별 매치 풀. 빠른 시작 / 방 만들기 / 트랙 직접 선택.
- **대기 30초 안에 인원이 차지 않으면 그대로 시작한다.** 혼자면 타임어택이 되고, 고스트가 상대 자리를 채운다. 사람을 기다리게 하는 로비가 가장 먼저 죽는다.
- **봇은 레이스에 넣지 않는다.** `backend/scripts/bot-sim`이 있지만, 봇 성적이 순위에 섞이면 순위표의 의미가 사라진다. 빈자리는 고스트(과거 사람 기록)로 채운다. 고스트는 실제로 있었던 기록이므로 정직하다.

## 6. 하지 않을 것

| 항목 | 이유 |
| --- | --- |
| 1. 아이템·우연 요소(랜덤 가격 충격, 운에 좌우되는 보정) | 사행성 판단의 핵심 요건이 우연성이다(03 §2). 거래 결과에 난수를 넣는 순간 "기술·규칙 준수 중심 평가"라는 완화 조치가 무너진다 |
| 2. 확률형 아이템·뽑기 | 확률형 아이템 규제 대상이 된다. 게임 레이어에 영구 비도입 |
| 3. 현금 환산 가능한 포인트·게임머니 | G0는 보상 없음이 원칙이다(02 §2.1). 환산 가능한 재화가 생기면 그 순간 G2 논의로 넘어간다 |
| 4. 성능에 영향을 주는 보상(한도 완화, 레버리지 증액, 수수료 할인) | 참가자마다 조건이 달라지면 순위가 실력 지표가 아니게 된다. 규칙 투명성 포지셔닝(01 §4)과 충돌한다 |
| 5. 실시간 시세 레이스 | 지연 차익과 복사거래 벡터를 제품이 직접 만든다(03 §3 부정거래). 트랙은 과거 구간만 쓴다 |
| 6. 순위 보상(상금·경품) | 경품 제공 자체가 별도 규제 검토 대상이다(02 §2.1에서 이미 내린 결정) |
| 7. 레이스 성적과 유료 평가 가격 연동(성적 할인) | 성과가 결제 유인과 묶이면 사행성 쟁점으로 바로 간다. G1 의견서 질의 항목으로 넘긴다 |

### 법률 질의 항목 추가 제안 (03 §2 표에 추가)

| 쟁점 | 질문 |
| --- | --- |
| 게임산업법 — 게임물 해당 여부 | 거래 시뮬레이션에 경쟁·순위·등급 요소를 붙인 서비스가 게임물에 해당해 등급분류 대상이 되는가 |
| 사행성 게임물 | 결과가 거래 실력에 기반하고 환전 가능한 재화가 없을 때에도 경쟁·순위 구조가 사행성 판단에 영향을 주는가 |

이 두 항목의 답을 받기 전까지 게임 레이어는 **무료·보상 없음·환전 없음**을 유지한다. 이 상태로는 G0 범위 안이다.

## 7. 릴리스 순서

| 단계 | 산출물 | 완료 기준 |
| --- | --- | --- |
| **R0 개념 검증** | 트랙 1개를 JSONL에서 잘라 고정, 1인 타임어택, 고스트·로비 없음. 기존 `trader.html`을 그대로 쓴다 | 3명이 같은 트랙을 각각 10회 이상 플레이하고, "한 판 더"가 실제로 일어나는지를 관찰 기록으로 남긴다. 여기서 재미가 없으면 R1 이후를 만들지 않는다 |
| **R1 트랙·매치 도메인** | `tracks`·`matches` 테이블, `sim_inputs.match_id`, 매치 스코프 호가 적용, 결과 확정, 재생 검증 | 같은 매치를 두 번 재생한 결과가 센트까지 동일. 기존 실시간 경로 회귀 없음 |
| **R2 동시 레이스** | 로비, 빠른 시작, 실시간 순위 SSE, 종료 정산, 커스텀 룸 | 4명이 10분 트랙을 동시 완주. 1명을 강제 종료시킨 뒤 재접속해 같은 순위로 복구 |
| **R3 고스트·리플레이** | 에쿼티 곡선 겹치기, 트랙별 기록 보드 | 내 기록을 고스트로 재생했을 때 체결 시각과 곡선이 원본과 일치 |
| **R4 라이선스·티어** | phase 화면화, 레이팅, 시즌 티어 | 승급·강등 경계 예시가 명세와 센트·점수 단위로 일치 |
| **R5 코스메틱** | 배지·프로필 테마, 업적 | 구매 경로가 없고 성능에 영향을 주지 않음을 테스트로 확인 |

**R0을 먼저 하는 이유**: 짧은 매치가 재미있는지는 문서로 증명되지 않는다. 트랙 1개와 기존 화면만으로 하루 안에 확인할 수 있고, 실패하면 R1~R5 전체를 안 만들면 된다.

기존 로드맵(04 §1)과의 관계: **보류 중이라 현재 로드맵에는 R0~R5가 들어 있지 않다.** 위 표는 재개할 때 쓸 순서일 뿐이고, 0.4·0.5와 평행하게 진행한다는 계획은 2026-11-23에 철회했다(머리말 보류 배너).

### R0 현재 상태 (보류 시점, 2026-11-23)

도구는 만들었고 **관찰은 하지 않았다**. 완료 기준(3명 × 10회 플레이 관찰 기록)은 열린 채로 멈춰 있다.

| 조각 | 상태 | 어디에 |
| --- | --- | --- |
| 트랙 추출 | 동작 | `data` `npm run track:extract` (`scripts/track.js`, 경계 테스트 7건) |
| 첫 트랙 | 있음 | `data/tracks/BTC-PERP/btc-perp-20261123-1200-300s`(5분·600호가, **합성 가격**) |
| 트랙 재생 | 동작 | `backend` `npm run dev:sim -- --track <파일> --speed 5` |
| 플레이 | 기존 `/trader.html` 그대로 | 계정 개설 → 주문 → 체결 → 한도 판정 → 종료 요약 확인 |

```sh
cd backend && npm run dev:sim -- --track ../data/tracks/BTC-PERP/btc-perp-20261123-1200-300s.jsonl --speed 5
```

R0에서 드러난 것 두 가지.

- **첫 트랙의 가격은 합성이다.** 작업 환경에서 거래소 피드에 접근할 수 없어 시드 고정 랜덤워크로 아카이브를 만들었다(`infra` 엔지니어링 로그 L-006). 포맷·추출·재생 경로는 실제 아카이브와 같다. 다만 **난이도 등급과 플레이 통계는 합성 트랙으로 내지 않는다.**
- **트랙이 끝나도 포지션이 남는다.** 시즌 상품에 `flat_at_close`가 없어서다. 3.2절의 "마지막 호가에서 강제 청산"은 R1의 매치 종료 처리에서 규칙으로 넣는다.

## 8. 저장소별 책임

| 저장소 | R0~R1 | R2~R3 | R4~R5 |
| --- | --- | --- | --- |
| `data` | 보관 JSONL → 트랙 파일 추출 도구, 트랙 스키마, 난이도 사후 집계 | 트랙별 플레이 통계 | 레이팅 분포 검증 |

| `infra` | 트랙 파일 보관 위치와 용량 | 매치 동시성 부하 점검 | — |
